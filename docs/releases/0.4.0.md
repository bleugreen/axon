# Axon 0.4.0

0.4.0 replaces the macOS daemon. `Axon.app`'s main executable, `Contents/MacOS/Axon`, is now the
Rust daemon `axon-mac`, the same architecture the Windows and Linux daemons already had, built over
the shared `axon-core`. The Swift daemon that served macOS through 0.3.6 is deleted. Swift remains
the language of the macOS clients: the `axon` CLI, the menu bar app, and the editor.

The bundle identifier stays `com.bleugreen.axon` under the same signing team, which is the identity
macOS records Accessibility and Screen Recording grants against, so an upgrade carries both grants
across without a new approval. The download, the archive name, the Homebrew cask, and the install
paths are unchanged.

## What you will see

**The menu bar icon is its own app.** `Axon.app` now holds four pieces: the daemon (its main
executable and the only process macOS grants anything to), `Axon Menu.app` (the menu bar app, which
holds no permissions), `Axon Editor.app`, and the `axon` CLI. The daemon and the menu run as two
login items, the launchd jobs `dev.axon.daemon` and `dev.axon.menu`, which Axon installs, restarts,
stops, and removes together.

**Quit Axon Menu quits only the menu.** The daemon keeps serving agents. The menu stays quit until
you open `Axon.app` again or run `axon start`. Nothing in the menu stops the daemon; `axon shutdown`
does, and `axon daemon uninstall` removes both login items.

**Opening Axon.app starts Axon rather than a second copy of it.** Opening the app from Finder,
Spotlight, or `open` runs the bundled `axon start` and exits. On a first open, or the first open
after dragging 0.4.0 over a 0.3.x install, that registers this copy's daemon and menu and starts
them. On a later open it starts whichever of the two is not running, which is how a quit menu comes
back. If a different copy of Axon is registered, it changes nothing, starts that copy's menu, and
prints how to switch: **Use This Copy** in this copy's menu, or this copy's
`Contents/Resources/bin/axon daemon install`.

`axon status` and `axon status --json` now report both login items, and the health document names
the implementation that answered: `daemon.provenance` carries the backend (`rust-axon-mac`), the
executable serving, its process id, and its version, and `daemon.shellContract` is the version of
the daemon-to-menu contract. See [Embedding Axon](../embedding.md) for the fields.

## What is unavailable on macOS in 0.4.0

These were accepted as degradations of the change rather than reasons to keep the Swift daemon.
Each is reported as a typed answer, not a silent failure.

- **`drag`.** The CLI, the SDKs, and the MCP tool list keep the verb, and the daemon refuses it with
  JSON-RPC `-32004`, capability `PointerDrag`, reason `not-implemented`. No platform implements drag
  now.
- **The editor's step debugger.** The daemon refuses `debug.*` with `-32004`, capability
  `DebugSession`. The editor then disables Debug and Run to Selected and says "Step debugging isn't
  available with this Axon daemon yet". Breakpoints stay in the document. Record From Here, which
  needed a paused debug session, now records before the selected step, and asks which application
  to record with the same picker the menu uses. Porting the debugger into the platform-neutral
  `axon-core`, which would also bring it to Windows and Linux, is follow-up work.
- **`observeChanges`.** Health reports this capability unusable with `not-implemented` even when
  every permission is granted, because the Rust daemon has no Accessibility event observer.
  `look(since:)` still works, by comparing a fresh capture with the retained one, and
  `wait_for_value` and `wait_for_stability` work by polling.

Screen text (`look` with `screenText`) is implemented on macOS through Vision but has no evidence
yet from the shipping bundle; the live verification lane and the release's signed qualification
check it. If recognition fails on your machine, `look` still succeeds and reports why in
`screenTextUnavailable`.

## `axon refresh-secrets` is retired

Axon no longer redacts values from a 1Password-backed index. It redacts only secrets bound to a
run's arguments and values matching its deterministic credential patterns. `axon refresh-secrets`
now exits with an error that says this.

Two behaviours went with the index. `look` no longer redacts a 1Password item's value that appears
in an application's accessibility text or recognized screen text, and it no longer withholds a
screenshot because such a value is visible on screen. If an agent may see windows that display
secrets, keep those windows out of what it is pointed at.

The first `daemon install` of 0.4.0 deletes the index file an earlier release left at
`~/Library/Application Support/Axon/active-credential-index.json` and prints that it did. That file
held HMAC digests and is inert without its key. The key stays in your Keychain, because deleting
another program's Keychain item can raise a prompt in the middle of an upgrade that is otherwise
silent. Remove it with:

```sh
security delete-generic-password -s com.bleugreen.axon.active-credential-index -a hmac-key-v1
```

## Updating

The menu's **Check for Updates** now also requires a downloaded release to carry the nested
`Axon Menu.app` (`com.bleugreen.axon.menu`) at the same version, beside the daemon, the CLI, and
the editor, and refuses one that does not. The update still finishes by running the new bundle's
`Contents/Resources/bin/axon daemon install` from the one-shot `dev.axon.updater` job, which now
registers both login items. The menu also no longer stops a finisher that is still running, which
could cut an install off part-way through.

After a drag install over a running 0.3.x, or after `brew upgrade` from the command line, run
`axon start` once; it sees the 0.3.x registration and re-registers both jobs from the new bundle.
Opening `Axon.app` does the same once the 0.3.x app is no longer running, but while it runs,
macOS may only bring the running 0.3.x forward.

## Going back to 0.3.6

0.3.6 knows nothing about the menu login item, so remove it before registering the 0.3.6 bundle:

```sh
launchctl bootout gui/$(id -u)/dev.axon.menu
rm ~/Library/LaunchAgents/dev.axon.menu.plist
/path/to/0.3.6/Axon.app/Contents/Resources/bin/axon daemon install
```

Without the first two lines, the 0.4.0 menu keeps running over the 0.3.6 daemon and shows
"Incompatible daemon", because a 0.3.6 daemon publishes no menu contract.

## For developers

- `axon serve` is deleted. Run a development daemon with
  `cd rust && AXON_SOCKET_PATH=/tmp/axon-dev.sock cargo run -p axon-mac -- serve`.
- `daemon install` refuses from a CLI outside `Axon.app`. Package with `scripts/package-app`, which
  now needs both cargo and Swift, and install from the bundle it builds.
- `scripts/check-app-layout` is the one definition of the bundle layout, run by the package smoke
  test and, with `--team`, by the release job on both the stapled bundle and the archive.
  `scripts/check-version` also covers `schema/tool-surface-v1.json` and the `axon-mac` crate.
- The recordings and browser answers the Swift daemon produced
  (`rust/axon-core/fixtures/swift-*`, `schema/fixtures/browser`) are now a frozen compatibility
  corpus: never regenerated, and replayed or matched by the Rust daemon in CI. The macOS health
  fixtures are generated from `axon-mac`'s own code path.

Before release the change goes through a signed qualification on a bench machine, first against
private launchd labels with the production install untouched and then as a real in-place upgrade
from 0.3.6. The driver is `scripts/macos-cutover-qualification`, and its evidence is recorded in
`scripts/macos-toolkit-acceptance/live/axn125/`. See [Install Axon](../install.md) and
[Embedding Axon](../embedding.md) for the full lifecycle.
